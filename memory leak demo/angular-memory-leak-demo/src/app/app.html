1. The Root Cause: Why Angular Memory Leaks Happen

In Angular applications, components have a lifecycle managed by the Angular framework. When an @if or *ngIf condition evaluates to false, or when a user navigates to a different route, Angular:

  1. Calls the component's ngOnDestroy() lifecycle hook.
  2. Removes the component's HTML element from the browser DOM.
  3. Destroys the component's change detector and internal Angular view structures.
The Critical Mistake: Removing a component from the DOM does not mean it is garbage collected! If any global object (such as window, document, or a root singleton service) holds a reference to the component or its methods, V8's Garbage Collector treats the component as reachable from the GC root.

2. The Retaining Reference Graph

+-------------------------------------------------------+
|  GC ROOT: Browser Global 'window'                     |
+-------------------------------------------------------+
                           |
                           | holds event listener table
                           v
+-------------------------------------------------------+
|  Resize Listener Callback (Closure)                   |
+-------------------------------------------------------+
                           |
                           | captures `this`
                           v
+-------------------------------------------------------+
|  Destroyed Component Instance (LeakingDemoComponent)  |
+-------------------------------------------------------+
                           |
                           | owns property `payload`
                           v
+-------------------------------------------------------+
|  LeakedPayload (Holds Array of 3,000 strings)         |
+-------------------------------------------------------+
   ===> ENTIRE SUBTREE IS PINNED IN HEAP MEMORY FOREVER!

Because window is never garbage collected, any closure registered on window keeps its captured scope alive. Each time a user visits and leaves a leaking view, another component instance and its memory payload are permanently stranded in the heap.

3. Code Comparison: Leaking vs Fixed

❌ Leaking Implementation
// Component mounts
ngOnInit(): void {
  // Arrow function closes over 'this'
  this.windowResizeHandler = () => {
    console.log(this.payload.marker);
  };
  window.addEventListener('resize', this.windowResizeHandler);
}

// Component unmounts
ngOnDestroy(): void {
  // ❌ FORGOT to call removeEventListener!
  // window still holds this.windowResizeHandler.
  // Component is unmounted from DOM, but lives forever in heap!
}
✅ Fixed Implementation
// Component mounts
ngOnInit(): void {
  // Exact function reference stored on instance
  this.windowResizeHandler = () => {
    console.log(this.payload.marker);
  };
  window.addEventListener('resize', this.windowResizeHandler);
}

// Component unmounts
ngOnDestroy(): void {
  // ✅ Cleanly unregisters the exact reference
  if (this.windowResizeHandler) {
    window.removeEventListener('resize', this.windowResizeHandler);
  }
  // All references from window are broken!
  // V8 can now safely collect this component and payload.
}

Chrome DevTools Heap Profiling: Step-by-Step Proof

To prove a memory leak scientifically to your mentor, you must not rely merely on console logs. You must capture Heap Snapshots in Google Chrome DevTools to show retained objects in the V8 heap.

Step 1

Open Chrome DevTools

Press F12 or Ctrl + Shift + I (Mac: Cmd + Option + I). Navigate to the Memory panel.

Step 2

Take Baseline Snapshot (Snapshot 1)

Select Heap snapshot → Click Take snapshot. This establishes your baseline memory before opening any demo components.

Step 3

Exercise the Leaking Component

Click "Cycle 5x" on the Leaking Component (or manually open and close it 5 times). Ensure it is currently unmounted (closed).

Step 4

Force Garbage Collection & Take Snapshot 2

In the DevTools Memory panel, click the Trash Can icon ("Collect garbage") at the top left to force a major V8 GC cycle. Now click Take snapshot.

Type LeakedPayload or LeakingDemoComponent into the Class filter box.
Observation: You will see 5 instances still retained in memory! Click on any instance and look at the Retainers panel at the bottom: you will see the retaining path rooted at window.addEventListener.
Step 5

Exercise the Fixed Component

Click "Cycle 5x" on the Fixed Component. Ensure it is currently unmounted (closed).

Step 6

Force Garbage Collection & Take Snapshot 3

Click the Trash Can icon again. Click Take snapshot.

Type CleanPayload or FixedDemoComponent into the Class filter box.
Observation: Exactly 0 instances exist! The browser's garbage collector successfully reclaimed all 5 instances because the reference was cleanly severed in ngOnDestroy().

Summary Matrix for Mentor Presentation

30-Second Summary for your Mentor:

"In Angular, unmounting a component from the DOM only tears down its template view; it does not destroy JavaScript object references held globally. Because the leaking component registered a listener on the global window object and failed to remove it in ngOnDestroy(), the window object's event listener table permanently retained the closure, the component instance, and its entire data payload. In our fixed version, we store the listener reference and invoke window.removeEventListener inside ngOnDestroy(), breaking the retain chain and allowing the V8 engine to collect the memory during the next GC cycle."
